## 3. Corrections

**The AI corrected me**
- Growth is **linear** in the number of plans, not exponential; the pain is the 1-minute cost per plan. I also mixed up minutes and hours in my first calculation.
- Speed is limited by what the other team can handle, not by how many threads I use.
- With branching versions, "newer" cannot be a number comparison.
- A later version contains the earlier ones, so "accept some versions and not others" does not work.
- A message queue is for telling, not for storing; a cache is not a record.
- A list of changes per version is a history, not the net effect the user needs.

**The independent review corrected the AI's drafts**
- **Design gap:** engagements never loaded have no product or market, so a publish cannot find them. The worker became a job-based "resolve this engagement" task, run for backfill, sampling and post-publish checks.
- **Worker bugs:** a timeout freed capacity while the other system was still working; throttle answers used up the retry attempts; there was no shared capacity limit across jobs.
- The target for wrong "up to date" answers (1 in 10,000) could not be measured in practice, so it became 1 in 1,000.
- Summary checks cannot catch a reversed meaning; the cost model ignored markets and reviewers; one cost figure did not match its own arithmetic; the "seconds" promise contradicted the 60-second target.

**The AI caught its own mistakes along the way**
- One test passed even when the bug was present. Putting a bug in on purpose showed it, and the test was strengthened.
- An LLM price came from an older model, and a DynamoDB price was stale. Both were corrected from current sources.
- While simplifying the cost table, the cost of the sampling checks turned out larger than first stated. The sample size per publish was reduced and the total recalculated.

## 5. Where AI should not be trusted in this domain

- **Numbers and prices.** Sources disagreed, and some prices were stale. A person must check them.
- **Facts about systems it cannot see** (the other team's EMS, its events, its capacity). These are assumptions to confirm.
- **Rules about regulation and retention.** "7 years" is an assumption.
- **Concurrency and failure handling.** Code that looks right hid real bugs.
- **Tests it writes.** A test can pass without testing anything; put a bug in on purpose to check.
- **Consistency across documents.** Drafts written at different times contradicted each other.
- **The meaning of generated summaries** shown to users of an audit product.

## 6. How I would guide other engineers using AI here

1. Treat AI output as a draft. A person writes and owns each design decision.
2. Mark every number and claim as fact, assumption or opinion, and replace placeholders.
3. Get a second, independent review, and ask it to find contradictions instead of rewriting.
4. For tests the AI writes, break the code on purpose to see the test fail.
5. Never send client content to a model; only template differences.
6. Keep summaries auditable: the exact list always shown, immutable records with model and prompt versions, and expert review for risky changes.
7. Keep a log of where AI helped and where it was corrected.
